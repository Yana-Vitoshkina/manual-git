## Ключевые понятия

| Термин | Что это |
|---|---|
| Репозиторий | Хранилище проекта и всей истории его изменений |
| Коммит | Снимок состояния файлов в определённый момент, «сохранение» с пояснением |
| Рабочая директория | Текущие файлы проекта, в которых вы работаете |
| Индекс (staging area) | «Площадка» для подготовки файлов к коммиту |
| HEAD | Указатель на текущий коммит (обычно на последний в ветке) |
| Ветка | Независимая линия разработки |
| Origin | Стандартное имя удалённого репозитория (GitHub и т. п.) |
| Хеш коммита | Уникальный идентификатор коммита, например `a1b2c3d` |

## Регистрация на GitHub

1. Перейти на github.com и создать аккаунт (логин, почта, пароль).
2. Настроить Git на компьютере — записать своё имя и почту, чтобы они попадали в коммиты:

```bash
git config --global user.name "Ваше Имя"
git config --global user.email "почта@example.com"
```

3. Проверить настройки:

```bash
git config --list
```

4. Для отправки кода на GitHub настроить SSH-ключ (рекомендуемый способ):

```bash
ssh-keygen -t ed25519 -C "почта@example.com"   # создать ключ
cat ~/.ssh/id_ed25519.pub                        # скопировать публичный ключ
```

Публичный ключ вставить в GitHub: Settings → SSH and GPG keys → New SSH key.
Проверить связь:

```bash
ssh -T git@github.com
```

## Инициализация проекта

```bash
mkdir my-project && cd my-project   # создать папку и перейти в неё
git init                            # сделать папку git-репозиторием
```

Что важно знать:

- `git init` создаёт скрытую папку `.git` — в ней живёт вся история проекта. Удалять её руками не нужно.
- Файл `.gitignore` — список файлов, которые Git не должен отслеживать (пароли, кэш, временные файлы).
- Проверить состояние репозитория: `git status`.

Клонировать уже существующий репозиторий:

```bash
git clone git@github.com:username/repo.git
```

## Работа с коммитами

Три шага: изменить файлы → подготовить их → сохранить.

```bash
git status          # что изменилось, что подготовлено
git add file.txt    # подготовить один файл
git add .           # подготовить все изменения
git commit -m "Сообщение о том, что сделано"  # сохранить изменения
git log             # история коммитов (q — выход)
git log --oneline   # краткая история: хеш + сообщение
git diff            # что именно изменилось, но ещё не подготовлено
```

Правила хорошего сообщения к коммиту:

- коротко и по делу: что изменилось и зачем;
- в повелительном наклонении: «add feature», «fix bug», «добавить тесты»;
- одно логическое изменение — один коммит.

## Работа с удалённым репозиторием

Создать новый репозиторий на GitHub (кнопка New repository) и связать его с локальным проектом:

```bash
git remote add origin git@github.com:username/repo.git  # связать репозитории
git remote -v                                           # проверить связь
git push -u origin main                                 # отправить локальную историю на GitHub
git push                                                # все следующие отправки
git pull                                                # забрать изменения с GitHub
```

Алгоритм первого коммита и загрузки на GitHub:

1. Создать репозиторий на GitHub (пустой, без README).
2. `git init` в локальной папке.
3. Добавить файлы, например `README.md`.
4. `git add .` и `git commit -m "first commit"`.
5. `git branch -M main` — переименовать ветку в main, если она называется master.
6. `git remote add origin <адрес репозитория>`.
7. `git push -u origin main`.

Проверить, что версии идентичны:

```bash
git fetch        # обновить данные о удалённом репозитории
git status       # должно быть: "Your branch is up to date with 'origin/main'"
```

Ту же проверку удобно сделать командой `git log origin/main..main` — пустой вывод означает, что локальная ветка не опережает удалённую.

## Ветвление

```bash
git branch                      # список веток
git branch new-feature          # создать ветку
git checkout new-feature        # переключиться на ветку
git switch new-feature          # современная команда для того же
git switch -c new-feature       # создать и сразу переключиться
git merge new-feature           # влить ветку в текущую
git branch -d new-feature       # удалить ветку после слияния
```

Типичный сценарий: для каждой новой задачи — отдельная ветка от main, работа в ней, потом слияние.

## Отмена изменений

```bash
git restore file.txt            # отменить изменения в файле (до индексации)
git restore --staged file.txt   # убрать файл из индекса, изменения останутся
git commit --amend              # дополнить последний коммит
git revert <хеш>                # отменить коммит новым коммитом (безопасно)
git reset --hard <хеш>          # откатить всё к коммиту (осторожно: удаляет изменения!)
```

## Полезные команды на каждый день

```bash
git help <команда>    # справка по любой команде
git status            # что происходит прямо сейчас
git log --graph       # история с графом веток
git show <хеш>        # подробности конкретного коммита
git stash             # временно спрятать незаконченные изменения
git stash pop         # вернуть спрятанное
```

## Памятка

- Всегда смотреть `git status` перед действиями — Git подскажет, что делать.
- Коммитить маленькими шагами с понятными сообщениями.
- Перед `push` — сделать `pull`, если могли измениться данные на GitHub.
- Не бояться Git: почти всё можно откатить, особенно через `git revert`.
